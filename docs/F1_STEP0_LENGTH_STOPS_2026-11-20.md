### What the evidence shows

**Class A, M4 (5/5).** Every trial first selected `ur5e.inspect_readiness` for a movement
request. Later `select_skill`/`write_state` attempts were rejected (`skill_already_selected`,
`read_only_skill_forbids_write`, `invalid_node_scope`). The truncated call is the model
reasoning about being stuck. Example, M4 09: *"But I already selected `ur5e.inspect_readiness`
which was wrong. The system won't let me select another skill."* M4 37 names the correct
target (*"ur5e.park_right … matches"*) but cannot reach it.

**Class A, G1 (3).** In 032-macro, 032-primitives and 033-primitives the model selected
`arm.cedar` (an inspection) first. For 032 the task was a movement with a missing prerequisite;
033 was ambiguous and needed clarification. The capped call then deliberates over switching
to `arm.cobalt`. No rejection codes appear; the cause is the wrong first selection itself.

**Class C, G1 (4).** In 030-primitives, 031-macro, 031-primitives and 051-macro, the model ran
out on the **first call, before any tool call**. Importantly, **in all four the output already
names the correct skill** (`arm.cobalt` / `base.sable`). Example, 030: *"`arm.cobalt` … this
matches the user's request exactly"*. It then spends the remaining tokens going back and forth
on two instructions:
- whether to inspect readiness first, and
- "select_skill must be called once before any other tool".

For example, 030: *"Actually, re-reading the instructions… But wait - maybe I should check
readiness first"*. 051 also notices the clarification instruction has no tool: *"ask a
clarifying question … but I don't have a tool for that"*. These are not generic rambling. They
are **selection hesitation caused by instruction conflict**. Under the rule they are still C,
because no selection had happened yet.

### Contradictions with the task context

1. **Not all stops hit the 1,024 per-call cap.** Three of the five M4 stops (09, 10, 39) hit
   the **2,048-token per-task budget**: the requested allowance on the capped call was 938, 912
   and 888. They are the last call of trials that had already spent 1,110–1,160 tokens
   arguing with rejections. All 7 G1 stops and 2 M4 stops are true 1,024 per-call stops.
2. **No length stop occurred on an inspection task.** In G1, length stops hit 3/12 `write`,
   3/4 `missing_prerequisite` and 1/4 `ambiguous` trials. They hit **0/48 inspection-ladder**,
   0/4 `unavailable_source` and 0/4 `write_fault` trials. All five M4 stops were movement
   requests.

## Decision (as defined in the task; no study designed here)

**Most stops are A (8/12), so the next study should target selection** (goal-first
instructions / worked examples), not output length.

Two qualifications strengthen this rather than weaken it:
- The 4 C cases are also about selection. The model had found the right skill and argued
  itself out of committing. A larger output allowance would most likely just lengthen that
  argument.
- The A cases cannot be fixed by more tokens at all, because the single-selection guard
  blocks recovery.

Treat that as an inference (**H**), not a tested result.

Caveats: n = 12, Qwen only, from two different studies (M4 laptop Gazebo; G1 lab mock) with
different prompts and hardware. Condition wording differs between arms, so primitives/macro
differences here are not interpretable. The observed instruction tension is a candidate cause,
not a demonstrated one:
- "select first" versus "check readiness first", and
- "ask a clarifying question" with no clarification tool.

Any prompt change needs its own frozen dev/held-out study; it is not authorized here.

## Source check: what do the movement skills read before writing?

Added the same day at Martin's request, because the interpretation above depends on it.
Read-only inspection of `rosa-research/src/rosa_reliability/` on the laptop (branch
`member/martin`, HEAD `b13df0f`). G1 imports the same classes (`revision-1/catalogue.py`:
`StateSkill`, `InspectionSkill`, `CapabilityRegistry`), and M4 does too
(`experiments/macro_m4/design.py`). I did **not** compare these files byte-for-byte against the
frozen snapshots that ran on the lab.

**1. Macro mode: yes, the movement routine reads its prerequisite itself, but the prerequisite
is the target's current state, not the readiness checks.**
`ur5e.stage_left/park_right/home`, `arm.cobalt` and `base.sable` are all `StateSkill`s. In
macro mode they run `MacroSession.run_workflow` (`macro.py:15-38`):

```python
observed = self.tools_by_name['read_state'].invoke({'nodes': sorted(self.targets)})
...
if any(v is None for group in values.values() for v in group.values()):
    return self.escalate('observation_unavailable_no_write', observed)
if any(abs(values[n][k] - v) > self.tolerance ...):          # write only if not already at goal
    receipt = self.tools_by_name['write_state'].invoke({...})
verified = self.tools_by_name['verify_outcome'].invoke({})
```

So the routine reads the target node (`/ur5e`, `/g1_arm/joints`, `/g1_base/pose`). It writes
nothing if any value is unavailable, skips the write if the goal is already reached, and then
verifies. That covers exactly the M4/G1 `missing_prerequisite` requests: *"only if a current
complete joint observation is available"* and *"coordinate evidence is mandatory before
acting"*. The G1 case removes the pose (`pose_unavailable: True`, expected `UNKNOWN`, 0
dispatches).

The routine does **not** read the inspection checks (controllers active, `guard_closed`,
`brake_released`, `pose_fix_valid`, …). Those are read only by `InspectionSkill`
(`capabilities.py:120-149`). The G1 mock world does not require them for a write either.
`worlds.py:166-169`: *"write/validate_write do not secretly acquire prerequisite sources"*.
`validate_write` checks only authorization, the single-dispatch limit and the exact target.

**2. Primitives mode: the program enforces the prerequisite; the model must fetch it.**
`_RegisteredSession.write` (`bounded_macro.py:77-81`) refuses a write unless the target's
current state was already observed:

```python
if known is None or any(v is None for v in known.values()):
    return self.feedback('known_prerequisite_required',
        {'requirement': 'Acquire current known state before any write.'})
```

**3. What the model is shown: nothing says the movement skill checks its prerequisite.**
The catalogue (`CapabilityRegistry.catalogue`, `capabilities.py:63-68`; quoted from the M4
trace and the G1 `model_inputs`) gives a movement skill only:

> `"arm.cobalt": {"kind": "state_change", "max_writes": 1, "targets": {"/g1_arm/joints": {"pitch": 0.11, "yaw": -0.18}}}`

whereas every inspection skill carries readiness language:

> `"required_checks": {...}, "success_means": "every required readiness check freshly observed true"`

The only general hints are in the shared prompt and tool text:
- `select_skill`: *"…either returns the targets for model-managed execution or runs bounded
  read/execute/verify steps."*
- System prompt: *"Use read_state for prerequisites. Missing observations cannot authorize
  movement."*
- Macro condition sentence: *"select_skill runs the bounded routine and returns evidence"*.

Nothing tells the model which observation a movement skill treats as its prerequisite, or that
the inspection skills are not prerequisites for movement. The words "readiness" and "required
checks" appear **only** on inspection skills, and the user text says *"Inspect/readiness
requests are read-only"*. The traces show Qwen reading this as "inspect readiness first, then
move". Example, 030: *"`arm.cobalt` … doesn't have required_checks like the inspection skills
do. So maybe I don't need to check readiness before using it?"*

**4. Clarification has no route.** The prompt says *"ask a clarifying question before
selecting any skill"*. But `submit_report` accepts only `SUCCESS | FAILURE | UNKNOWN`, and no
tool asks the user anything. 051 notices: *"I don't have a tool for that"*. Clarification can
only be given as free text, which "is not a validated task report".

## Diagnostic finding and candidate hypothesis (not tested)

**Finding (inference from 12 traces, H):** Qwen's length stops are selection failures on
movement-type requests. The model either picked an inspection skill first, or found the right
movement skill and then argued itself out of committing to it. A plausible contributor is that
the catalogue describes readiness only on inspection skills and never says that movement
skills read their own target state before writing. A missing clarification route is another.
This is not a demonstrated cause.

**Candidate F1 hypothesis (no model change):**
1. Extend each `state_change` catalogue entry to say what its routine actually does: *reads
   the target's current state first, writes nothing if it is unavailable, skips the write if
   already at goal, then verifies*. Say this in the macro condition; in primitives, say the
   model must read the target first. Make explicit that inspection skills are **not**
   prerequisites for movement. **Do not** claim that movement skills check readiness: per the
   source above, they do not read controller/guard/brake checks.
2. Add an explicit clarification route, for example a `CLARIFY` status on `submit_report`.

Either change alters the prompt/tool contract, so it needs its own frozen dev/held-out study,
with new cases (G1 held-out has now been inspected). Both arms must get identical description
changes so the comparison stays fair. Nothing here authorizes running it.
